# 会话短期记忆与长期记忆设计

更新时间：2026-10-09

本文记录已商议的目标设计，不代表所有功能已经实现。目标是参考 Codex 风格的公开记忆思路，建立可持久化、可追溯、可更新的记忆模块；不声称复刻 Codex 应用内部实现。

## 一、目标与当前状态

当前实现：Streamlit 进程内保存页面会话和展示消息；FastAPI 内存字典按 session_id 保存最近 5 个成功问答轮次，用于指代消解。两个进程的数据均未持久化，服务重启后不能完整恢复。

目标要求：

- 短期与长期记忆均持久保存，关闭页面、重启服务或电脑后可恢复。
- 完整聊天记录保存到磁盘；给模型的上下文可以裁剪或压缩，但不能因此删除原始记录。
- 长期记忆支持自动提取保存，也支持用户明确要求“记住”时保存。
- 支持记忆查看、修改、删除、来源追溯与版本管理。
- 用户之间、会话之间保持明确隔离。

“短期”表示信息服务于当前会话，不表示数据临时保存；“长期”表示信息可跨会话复用。

## 二、记忆机制与存储机制的区别

| 维度 | 解决的问题 | 本项目方案 |
|---|---|---|
| 记忆机制 | 保存什么、何时整理、如何注入上下文 | 会话压缩、候选提取、整合更新、分层读取 |
| 存储机制 | 数据保存在哪里、如何组织和恢复 | PostgreSQL 主库，按需增加 Redis 缓存及文件视图 |

数据库持久保存所有原始记录，并不意味着每次把全部记录发送给模型。

## 三、会话短期记忆机制

### 1. 完整历史持久化

保存用户消息、助手回答、参考资料、消息状态和时间。执行失败保留错误状态用于展示及排查，但不作为成功回答进入模型历史。

会话列表和消息从后端数据库读取，替换当前仅依赖 Streamlit session_state 的恢复方式。页面刷新或服务重启后，可重新加载原会话。

### 2. 上下文预算与压缩

模型上下文采用：会话摘要 + 近期完整问答 + 当前问题。

根据 Token 预算决定何时压缩较早消息，预留系统提示、检索资料、长期记忆和输出空间。阈值在实施时配置，不硬编码为模型窗口上限。

摘要重点保存：用户目标、对象与指代、明确约束、已确认信息、已完成事项、待办和未决问题。记录摘要覆盖到哪条消息，避免重复摘要或漏掉消息。

摘要生成失败时不推进覆盖位置；保留原文并使用预算内的近期轮次。摘要替换与覆盖位置更新需要一致提交。

### 3. 历史回查

近期消息及摘要不足以解释问题时，可按需读取当前会话更早的原文。回查只访问当前用户拥有的会话，限制返回数量和上下文长度。

### 4. 工作流接入

结合摘要和近期消息补全指代，再执行本地检索。分别保存用户原始问题、指代消解后的完整问题、检索过程中再次改写的问题，便于排查。

压缩只改变模型输入视图，不改变聊天记录本身。

## 四、长期记忆机制

### 1. 保存范围

适合保存：稳定的回答偏好、用户明确表达的项目背景、已确认的重要事实、可复用的工作方法与经验。

半导体技术资料继续以知识库为依据；不能默认把全部聊天、模型推测或未核实的技术结论固化为用户事实。

### 2. 两种写入入口

自动入口：普通聊天 → 提取候选 → 判断稳定性和证据 → 去重及冲突检查 → 保存。

显式入口：用户说“记住……” → 提取指定内容 → 保存 → 反馈具体保存内容。

用户要求自动保存，不要求每条候选都人工审批。证据不足、含义不清或互相冲突时保留待确认状态，不擅自合并成确定事实。

### 3. 去重、更新与版本

同义重复内容合并；新内容修正旧内容时更新有效版本并保留修改记录。区分用户明确修正和系统推断，不采用简单的“最后一句永远覆盖”。

每条记忆关联用户、来源会话及消息、类别、创建和更新时间、有效状态及版本。需要能解释记忆从哪里来。

### 4. 分层读取

第一层：简短用户记忆概况，例如回答偏好和正在进行的项目。

第二层：依据当前问题查找相关详细记忆。

第三层：需要更多证据时回查来源会话摘要或原始消息。

每层都有上下文预算；不把全部长期记忆放入每次请求。第一版可采用结构化和关键词查询，后续根据效果再引入向量检索。

记忆作为辅助上下文，不能覆盖用户当前明确要求，也不能作为知识库事实的替代来源。

### 5. 整理触发方式

显式“记住、修改、忘掉”及时处理；自动提取作为后台任务，在完整轮次结束或会话整理时触发。具体触发频率、队列和重试策略在实施时确定。

新建会话不删除旧会话，也不删除已保存的长期记忆。

## 五、存储选型

| 组件 | 定位 | 是否第一阶段需要 |
|---|---|---|
| PostgreSQL | 会话、消息、摘要、长期记忆与版本的唯一可信来源 | 是 |
| SQLAlchemy | 数据访问与事务管理 | 是 |
| Alembic | 数据库结构版本迁移 | 是 |
| Redis | 热点缓存、任务队列或并发协调，不承担唯一持久存储 | 后续按需 |
| Milvus | 现有知识库向量；可选的长期记忆语义索引 | 知识库保留，记忆索引后续评估 |
| Markdown / JSONL | 可读导出、审阅与回查视图 | 按需 |

不把长期记忆仅放入 Redis。缓存、向量索引和可读文件都应能由主库重建。

## 六、PostgreSQL 数据结构

以下为逻辑表设计，字段和索引在实现阶段细化。

| 表 | 内容 |
|---|---|
| users | 用户标识与记忆归属 |
| sessions | 会话 ID、用户归属、标题、状态及时间 |
| messages | 完整问答、顺序、执行状态、资料来源和请求标识 |
| session_summaries | 会话摘要、覆盖消息位置及摘要版本 |
| memory_candidates | 自动提取的候选及证据、处理状态 |
| memories | 当前有效长期记忆及类别、来源、状态 |
| memory_versions | 长期记忆历史版本和修改原因 |
| memory_jobs | 提取、整合等后台任务及重试状态 |

消息内容与业务索引明确区分；资料来源等结构化附加信息可用 JSONB 保存。用户归属、消息顺序及常用查询需要索引。

采用事务保证记忆更新和版本记录一致；不在数据库事务中长时间等待模型调用。后台任务需要幂等处理，避免重复消费产生重复记忆。

## 七、类似 Codex 风格的可读文件视图

可以从主库导出：

```text
memory_exports/
└── users/
    └── <user_id>/
        ├── memory_summary.md
        ├── MEMORY.md
        ├── sessions/
        │   └── <session_id>.jsonl
        └── session_summaries/
            └── <session_id>.md
```

| 文件 | 作用 |
|---|---|
| memory_summary.md | 简短记忆概况与详细记录索引 |
| MEMORY.md | 整合后的可复用长期记忆 |
| sessions/*.jsonl | 原始会话记录导出 |
| session_summaries/*.md | 会话摘要及回查线索 |

PostgreSQL 是唯一可信数据源。文件属于导出视图，不建立与数据库并行、独立修改的双主存储。导出记录生成时间与版本，更新时避免留下半写入文件。

## 八、持久化与删除一致性

- PostgreSQL 使用持久数据卷，正常服务重启不清除数据；持久化不等于备份。
- 定期数据库备份，并验证恢复；不得将删除数据卷当作普通重启操作。
- 用户请求删除记忆时，同时处理主库有效记录、检索索引、缓存及导出文件，避免旧记忆继续被召回。
- 修改历史、原始会话及备份的保留与彻底删除策略需明确；不能仅标记当前版本失效就宣称所有副本已删除。
- 数据读取始终验证用户归属，不能仅凭 session_id 访问他人记录。

## 九、与公开机制的对应及边界

公开文档中的上下文压缩为长运行保留后续需要的状态；本项目用千问生成文本摘要实现类似目的，不等同于 OpenAI 的不透明压缩状态。

公开 Sandbox Agents 文档展示分层记忆读取、候选提取和整合，以及 memory_summary.md、MEMORY.md、会话记录和摘要布局。本项目参考这些数据角色，以 PostgreSQL 持久保存，再导出类似可读视图。

没有公开依据确定当前 Codex 应用内部数据库选型，因此不宣称 PostgreSQL 或 Redis 是 Codex 的实际后端。
